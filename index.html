Overview

Source

Turn any repository into a living, validated project map. The map is a projection of evidence, not a novel.

Procedure

  1. Resolve the project: --dir (default cwd), project name from --name, then package.json, then the directory name.
  2. Gather evidence: graphify cache or deterministic scan; .specify/ if present; a security run if supplied.
  3. Project, never invent: map graphify nodes and relations 1:1, keep ids stable, tag derivation (graphify, speckit, security, llm). A skipped relation is a warning, not a guess.
  4. Write through the CLI, not by hand:

``bash node scripts/mapkeeper.mjs init|sync|audit|export|context|graph|specs|security|doctor|query|migrate ` The CLI owns validation, managed blocks, the vault, exports, and the ledger. Hand-writing graph.json is a last resort and must still pass scripts/validate-graph.mjs`.

  1. Report: mode, generation source, changed units, coverage counts, assumptions/unknowns, artifacts, next actions.

Non-negotiables

  • A tool is never reported as used unless it ran and its output parsed. If graphify is missing, say graphify-fallback or llm-manual.
  • Every non-inferred node needs source_refs or spec_refs. Inferred nodes need confidence and appear under *Unverified* in sync-summary.md.
  • Validation failure must not overwrite the previous good graph. The CLI writes the candidate to project-map/.cache/graph.candidate.json and exits non-zero.
  • Never write into .specify/, a security run directory, or a human-owned region of a vault note.
  • Never publish a security candidate whose verdict is rejected, and never assign severity to needs_validation.
  • Redact secrets to <redacted> and add an unknowns entry describing what was removed.

Adapters (optional, read-only)

Graphify: detect the graphify binary and graphify-out/graph.json. Run graphify update only when a cache exists and the user allows it (--run-tool); otherwise consume the cache. mapkeeper query delegates to graphify query|path|explain.

Spec-kit: detect .specify/; ingest constitution.md, spec.md, plan.md, tasks.md. Requirements get ids from FR-###/US#; tasks from T###; edges satisfies_requirement. Report requirements with no task and tasks referencing missing files. Never edit spec-kit artifacts.

Security audit: locate an installed security-audit skill and a run directory containing run-metadata.json, architecture.md, findings.json. Preserve verdicts; trust boundaries become nodes; findings link to files, boundaries, and requirements. Never run an audit implicitly.

Answering questions from the map

  1. Read project-map/obsidian-vault/02-LLM-Context.md first.
  2. If the question is about structure, use mapkeeper query (or graphify query) before reading source.
  3. Open only the node notes linked from the answer.

Validation

node scripts/validate-graph.mjs project-map/graph.json
node scripts/validate-ledger.mjs project-map/map-ledger.json
node scripts/validate-context.mjs project-map/obsidian-vault/02-LLM-Context.md

An audit exits non-zero when artifacts are invalid, a tracked path is absent from the ledger, a mapped unit's evidence is missing, or a requirement has no satisfying edge. Never claim full coverage without stating the ledger counts.

Final response

  1. Mode and phase.
  2. Generation source (graphify, graphify+llm, llm-manual, graphify-fallback).
  3. What changed or what the audit found.
  4. Coverage: mapped / stale / unmapped / out_of_scope.
  5. Assumptions and unknowns.
  6. Artifacts written.
  7. Risks and next actions.

Adapters

Graphify — detects graphify and graphify-out/graph.json, runs graphify update only when a cache exists and you allow it (--run-tool), projects nodes and relations 1:1, and never invents a relation. Background

A living project map for any repository: a validated knowledge graph, a coverage ledger, an Obsidian vault, and architecture exports.

The original version was a 1,300-line prompt that asked an agent to produce JSON it could not validate and to call Graphify tools that did not exist. This version is a skill plus a zero-dependency CLI. Every artifact has a schema, the coverage claim is falsifiable, and Graphify, spec-kit, and security-audit are optional adapters rather than assumptions.

Contract

Source

This file is the single source of truth for what Mapkeeper writes. SKILL.md, Mapkeeper_Prompt.md, and the HTML guide are generated from or must agree with this file.

Output layout (inside the user's repository)

your-project/
├── Mapkeeper_Prompt.md              # optional legacy shim, generated, deprecated
└── project-map/
    ├── graph.json                # schema v2 projection: machine truth
    ├── map-ledger.json           # coverage units + run history
    ├── architecture-overview.md
    ├── architecture-overview.json
    ├── architecture-overview.html
    ├── sync-summary.md
    └── obsidian-vault/
        ├── 00-Home.md
        ├── 01-Index.md
        ├── 02-LLM-Context.md
        ├── 10-Architecture/
        └── <kind folders>/

.DS_Store, graphify-out/, and project-map/.cache/ are never mapped.

Mandatory rules

  1. project-map/ is the only output directory. Do not use docs/project-map/, .project-map/, knowledge/, architecture-map/, or maps/.
  2. project-map/graph.json is the only graph of record. graphify-out/graph.json is a tool cache; it is never edited by hand and never committed as truth.
  3. project-map/map-ledger.json is the coverage record. A run that does not update it has not been audited.
  4. Never place generated artifacts outside project-map/, except the optional Mapkeeper_Prompt.md shim and the repository's own docs.
  5. Never write into .specify/ or into a security audit run directory. Both are read-only inputs.
  6. Never expose secrets, tokens, credentials, connection strings, or private keys in any artifact. Redact to <redacted> and add an unknown entry explaining what was removed.

Write rules (bind to these, not to prose)

Every generated Markdown region is wrapped in a managed block:

<!-- mapkeeper:begin id=<stable-id> -->
generated content
<!-- mapkeeper:end id=<stable-id> -->
  • Writers replace only the block body. Text outside blocks is human-owned and must survive every run.
  • A missing block is appended; an existing block is replaced; a new file is created with a heading, then the block.
  • scripts/check-managed-blocks.mjs fails on an unclosed or duplicate block id.
  • Per-node notes carry YAML frontmatter that is regenerated on every run. Human notes go under a ## Notes heading outside managed blocks.

02-LLM-Context.md is fully generated and budget-enforced: target ≤ 1,500 tokens, hard fail > 2,000 (scripts/validate-context.mjs).

Evidence rules

SituationRequired evidence
Node derived from graphifysource_refs: ["<file>#<loc>"] or source_refs: ["<file>"] copied from source_file
Node derived from spec-kitspec_refs: ["<spec path>#<FR/T/US id>"]
Node derived from a security runsource_refs: ["<file>:<line>"] and verdict
Node inferred by the modelconfidence (low/medium/high) and listed under *Unverified* in sync-summary.md

Ids are stable. Never rename an id because a label changed. Ids must match ^[A-Za-z0-9][A-Za-z0-9_.:-]*$. Namespaced prefixes: spec_<feature>_... for spec-kit, sec_<run>_... for security, decision_adr_... for decisions.

Failure rules

  • A tool is never reported as used unless it ran and its output parsed. Record meta.graphify.available honestly.
  • Graphify unavailable → deterministic source scan (files + import edges) + spec/security ingestion. Mark derivation: "llm" only for model-authored content.
  • Graphify failed mid-run → keep the previous graph, add a sync-summary.md warning with the exact error, and exit non-zero in --strict mode.
  • Validation failure → do not overwrite the previous valid graph; write to project-map/.cache/graph.candidate.json, report the error, exit 1.

Modes and phases

Source

Mode decision table

Pick the first match:

ConditionMode
project-map/graph.json missingINIT
User asks for review / validation / consistency / gapsAUDIT
User asks for full rebuild, handover, closure, or as-built exportFULL
Only exports are requestedEXPORT
Only the LLM context note is requestedCONTEXT
Only the graph is requestedGRAPH
.specify/ changed and no code changedSPECS
A security run directory is suppliedSECURITY
Anything else with an existing mapSYNC

An explicit flag wins: --mode init|sync|audit|full|export|context|graph|specs|security.

INIT

  1. Resolve project name (arg → package.json/pyproject.toml/directory name).
  2. Detect .specify/ and an existing security run directory; ingest if present.
  3. Detect graphify: binary on PATH, graphify --version, and graphify-out/graph.json. Run graphify update only when a cache already exists; never start a long extraction unasked.
  4. Project whatever graph data exists into project-map/graph.json.
  5. Seed map-ledger.json from tracked files, one unit per top-level tree plus root files.
  6. Write the vault, architecture exports, sync summary, and context note.
  7. Validate everything, then print the summary.

SYNC (incremental)

  1. Load ledger. Compute changed files from git (git status --porcelain plus the diff from ledger.source_revision when available).
  2. Mark only affected units stale. Units whose scope did not match remain untouched.
  3. Re-extract only stale units: graphify --update if a cache exists; otherwise rescan only those paths.
  4. Merge: new extraction replaces nodes for the rescanned paths; spec-kit and security nodes are preserved until re-ingested.
  5. Update the ledger and summary. Output only: changed units, added/removed/updated node ids, new gaps, warnings.

Never regenerate the whole vault. Rewrite only notes whose node ids changed or disappeared; delete notes for removed nodes only when they carry no human text outside managed blocks.

AUDIT

Read-only with respect to the graph. Produce a report and set the exit code:

  • Validate graph.json, map-ledger.json, 02-LLM-Context.md budget, and managed blocks.
  • Every tracked path must appear in the ledger as mapped, unmapped, or out_of_scope; a path missing from the ledger is a failure.
  • Every mapped unit's evidence file must exist.
  • Every requirement unit must have at least one satisfies_requirement edge or be reported missing coverage.
  • Report stale units, orphaned Obsidian links, nodes without refs, and findings marked stale.
  • Exit 0 when clean, 1 when any failure is found, 2 when inputs are missing. --soft forces exit 0 for exploratory use.

An audit never claims completeness beyond the ledger. State the coverage counts explicitly.

FULL

Same pipeline as INIT, but discard cached derivations for graphify- and scan-derived nodes and rebuild them. Preserve human text, spec-kit nodes, and security nodes unless --reset-specs / --reset-security is given. Write project-map/.backup-v1/ first when migrating a v1 tree.

EXPORT

Regenerate architecture-overview.{md,json,html} and the vault from graph.json. Fail if the graph is missing or invalid. Never modify graph.json.

CONTEXT

Regenerate 02-LLM-Context.md only. Must satisfy the context schema and the token budget.

GRAPH

Rebuild graph.json only. Includes spec-kit and security ingestion unless --no-specs / --no-security is set.

SPECS

Ingest .specify/ artifacts, merge into the graph, update requirement/task units, and write the traceability report.

SECURITY

Ingest one security run directory. Never run the audit itself unless the user explicitly asked for an audit; in that case delegate to the installed security-audit skill and state its output directory.

Phase handling

PhaseEmphasisStatus vocabulary
BEFOREgoals, scope, requirements, constraints, stakeholders, planned architectureplanned, unknown
DURINGimplementation, decisions, task state, drift between docs and codeimplemented, planned, unknown
ENDas-built, deviations, debt, operational notes, handoverimplemented, deprecated, unknown

Never present planned work as implemented. Anything inferred rather than read is labeled.

Token rules

The rules below are enforced or made mechanical, not requested:

  1. SYNC prints only deltas (from the ledger diff).
  2. 02-LLM-Context.md is the first context source for later questions; SKILL.md says so and the validator enforces its size.
  3. query delegates to graphify query|path|explain; the fallback traversal reads graph.json only, never the repository.
  4. Under a low context budget, read 02-LLM-Context.md and the affected node notes only.
  5. No artifact is duplicated across files: contract text exists once, in references/contract.md.

Final response format

  1. Mode and phase.
  2. Generation source: graphify, graphify+llm, llm-manual, graphify-fallback, plus spec-kit/security ingestion flags.
  3. What changed (or audit findings).
  4. Coverage: mapped / stale / unmapped / out_of_scope.
  5. Assumptions and unknowns.
  6. Artifacts written.
  7. Risks and next actions.

Graphify adapter

Source

Graphify is an optional external tool. It is never required; Mapkeeper always has a deterministic fallback.

Detection (honest, in this order)

  1. graphify --version on PATH → record the version. A missing binary is not an error.
  2. graphify-out/graph.json exists → a usable cache. Record graph_path.
  3. .specify/ and security runs are independent inputs; they do not imply graphify.

Set meta.graphify accordingly:

{ "available": true, "version": "0.9.x", "graph_path": "graphify-out/graph.json", "used_cache": true }

available means graph data was consumed. used_cache: false means the CLI was invoked this run.

Invocation rules

SituationAction
Cache exists, user passes --run-toolRun graphify update in the project root, 10-minute timeout
Cache exists, no --run-toolConsume the cache; note it in sync-summary.md
Cache exists, init modegraphify update is allowed (default behavior)
No cache, binary presentDo not start a full extraction unprompted; use the fallback and say why
--graphify manual or disabledNever invoke; use the deterministic fallback
Update failsKeep the previous graph, record the exact stderr, continue with the fallback if no cache

Never run graphify with --mcp automatically. MCP is for query-time delegation.

Projection (graphify → graph.json)

Node mapping:

graphify file_typeMapkeeper kind
codefile
document, paper, imagedocument
rationaledecision
conceptdata_entity
missing/unknownfile

Preserve, verbatim:

  • id (never rename, never add chunk suffixes)
  • label
  • source_file (relativized to the project root when it is absolute and inside it)
  • source_location
  • community (into provenance.community and tags)

Set derivation: "graphify", confidence: "high" for code and "medium" otherwise, status: "implemented" for code and "unknown" otherwise, provenance.relation_source: "EXTRACTED".

Edge mapping is 1:1 and only for these relations:

calls, implements, references, cites,
conceptually_related_to, shares_data_with,
semantically_similar_to, rationale_for

If graphify emits any other relation, skip the edge and add a warning naming it. Never translate an unknown relation into relates_to.

Keep confidence and confidence_score unchanged. Hyperedges are not projected in v2; count them in the warning list if present.

Deterministic fallback (llm-manual / graphify-fallback)

When no graph is available, the scan is intentionally simple and reproducible:

  1. One project node (project_root) and one file node per tracked text file, ids file_<sanitized-path-without-extension>.
  2. component nodes for top-level folders with 3+ files, edges contains.
  3. Import edges references (EXTRACTED, score 1.0) resolved from relative JS/TS import/require and Python import/from. Unresolvable imports are dropped silently; cross-language edges are never created.
  4. dependency nodes from package.json with depends_on edges from the project node.
  5. Ignored: project-map/, graphify-out/, node_modules/, .git/, .specify/, lockfiles, binary/media files.

The fallback does not invent call graphs, services, or data flows. If the user needs those, they must install graphify or provide a graph.

Incremental behavior

  • sync without a cache rescans only changed files (git status plus the diff from ledger.source_revision).
  • Units whose scope matched a changed file become stale before rescanning.
  • Nodes whose source_refs point at a changed file are replaced; untouched nodes are kept.
  • Non-git directories fall back to a full rescan; say so in the summary.

Query delegation

mapkeeper query "<question>" runs graphify query "<question>" when both the binary and the cache exist. mapkeeper query path a b and mapkeeper query explain node delegate to the same CLI. On failure, Mapkeeper prints the graphify error and traverses project-map/graph.json instead — it never falls back to reading the repository.

Rules enforced by validate-graph.mjs:

  1. Node ids are unique.
  2. A node whose provenance.relation_source is not INFERRED needs source_refs or spec_refs.
  3. An inferred node needs confidence.
  4. verdict: "rejected" must never appear.
  5. status: "needs_validation" must not carry severity; severity requires status: "confirmed".
  6. Edge endpoints exist and are not self-edges.
  7. meta.counts.nodes/edges equal array lengths.

Markdown sections

Do not run all six phases yourself, do not copy its SKILL.md/companion docs into this repository, and do not relax its sandbox requirements.

Ids: sec_<run-id>_<fingerprint>; fingerprints are preserved verbatim when present. If a record has no fingerprint or id, hash a sanitized title.

Tolerated findings.json shapes: a top-level array, or an object with findings, records, results, or items. Unknown shapes produce a warning and zero nodes.

Severity and verdict rules (non-negotiable)

  • Severity exists only for confirmed. needs_validation has zero severity and is displayed in its own table.
  • rejected never appears in graph.json, the vault, or the architecture export.
  • A confirmed finding without a concrete file/line still publishes, but with source_refs pointing at findings.json and a warning.
  • A finding whose run revision is older than a changed affected file is marked provenance.stale_source: true and reported in sync-summary.md.

What Mapkeeper adds

  • Traceability: findings tied to components and requirements.
  • Coverage: a finding's file must also be mapped by a ledger unit; audit reports findings in unmapped paths.
  • Handover: confirmed and needs-validation findings appear in the architecture overview and the vault, with their original evidence links.

What Mapkeeper must not do

  • Re-run exploit steps, reproduce candidates, or "verify" a finding itself.
  • Merge needs_validation into confirmed lists to make a report look complete.
  • Copy the upstream six-phase workflow, attack classes, or validators into this repository.
  • Write into the audit run directory.

"graph validation failed"

The previous valid graph.json is untouched; the rejected candidate is at project-map/.cache/graph.candidate.json.

  1. Read the first five errors — they are path-addressed ($.nodes[12].id).
  2. Common causes: duplicate id; inferred node without confidence; edge pointing at a missing node; severity on a needs_validation finding; counts out of date.
  3. Fix the input (usually an ingestion bug), rerun. Do not hand-edit graph.json to silence the validator.

Context note is over budget

02-LLM-Context.md is meant to be a pointer file. Move detail into component/requirement notes and link them:

- [[20-Components/component_api|API]]

Then mapkeeper context regenerates it. Never raise the budget to hide bloat; the hard limit is 2000 tokens.

Units are unmapped

  • A new directory appeared: sync reseeds path units automatically.
  • The files are binary/lockfiles: they are ignored by design; they should not be units.
  • The area is intentionally out of scope: set the unit to out_of_scope with a one-line reason in sync-summary.md human text. Do not delete the unit; audit treats a missing path as a failure.

Graphify says "no cache"

graphify binary present but no graphify-out/graph.json. Options:

  1. Accept graphify-fallback (file/import graph) and say so.
  2. Run graphify yourself, then mapkeeper graph.
  3. Run mapkeeper init --run-tool if you want Mapkeeper to call graphify update (only with an existing cache).

Never claim graphify was used when only the fallback ran.

A spec requirement has no task

This is a real finding, not a Mapkeeper bug. Fix the spec/tasks, or accept the gap in the summary. audit exits 1 until a satisfies_requirement edge exists.

Security findings are stale

The run's source_ref no longer matches the repository and an affected file changed. Re-run the audit, or accept stale_source: true knowingly. Never upgrade needs_validation to confirmed by hand.

Non-git directory

source_revision is worktree; sync cannot diff, so it rescans all files and marks every path unit stale before remapping. That is expected. Reports will show the coverage after remap, not a delta.

Migrating an old map

node scripts/mapkeeper.mjs migrate
node scripts/mapkeeper.mjs doctor

migrate copies the five artifacts into project-map/.backup-v1/, maps legacy type/relationship_type, skips unknown relations with warnings, writes schema v2, seeds the ledger, and regenerates the vault and exports. doctor --migrate does the same when a v1 tree is detected. Old Mapkeeper_Prompt.md users: the prompt is a deprecated wrapper over this skill; keep it if you like, but the CLI is authoritative.

Notes were deleted unexpectedly

Only --prune deletes notes, and only mapkeeper-managed notes whose content outside managed blocks is empty. If human notes were lost, restore from version control; Mapkeeper never writes outside blocks.

Nothing happens on sync

No changed files and no stale units. Check --dir points at the repository root, and that files are tracked (or the directory is not a git repo — then a full rescan runs).
